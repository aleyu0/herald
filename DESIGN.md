# Design Decisions

## 1. Auth check move

The initial implementation of `proxy.ts` validated each request by calling `supabase.auth.getUser(token)`. However, this meant that all resources being fetched needed to route through there, which caused Turbopack to open many simultaneous network calls while the page was compiling. The page never loaded and my laptop crashed since it was consuming more than 24GB of RAM. I tried using devtools to identify the issue but it was impossible to see what was happening, let alone download an HAR. At this point I worked with Codex, which asked to curl the webpage. I approved it and as expected, my laptop froze again, but in this case the agent was able to identify the root cause as Turbopack's asset compilation triggering the auth calls. I swapped it for a cookie presence check in the proxy, leaving FastAPI to do the single token validation per actual API call.

## 2. Deduplication pipeline

The deduplication pipeline involves a couple of stages to ensure that the same event isn't added in the public feed multiple times. I used GenAI to list different methodologies and I tested each with a test dataset that included a screenshot of an event flyer, a cropped version of the same image, a straight on photograph of that flyer, and another photograph of that picture from an angle. This revealed which processes were needed. For example, while pHash is able to identify two identical images and provide a distance value if it's in someway cropped, it's less effective when a flyer is photographed at an angle. The Hamming distances for the flyers shot at different angles were between 32 and 36 which overlapped with a completely different flyer which was between 22 and 38. So I decided for this method to only inspect if an image is exact same as another. Another method I tested was using OCR pytesseract to get the text of the flyers before running it via the LLM model. This was a suggestion made by one of my classmates in A2, and is also aimed to reducing costs since if the text of the title and the dates are exactly the same, we can skip the LLM call. However, when I checked the output of that process, the outputs weren't accurate and were often unreadable. Especially with images taken with a camera, the outputs don't match from one image to the other. And finally, field extraction comparison after LLM extraction looks for similarities in event details so if the fields match with an existing public event, it would be flagged. I ended up using the pHash and field comparison to flag possible duplicates.

## 3. Duplicate scoring for fields

Since events share names, organizers, or locations, we need a way to ensure that false positives don't block users from being able to use the platform. I implemented a scoring system where it assigns a weighted value (0.6 for title, 0.2 for organizer, and 0.2 for location) when they match. However, there may be event entries where the organizer or the location isn't available. Comparing two fields null vs null provides a 100% match, so it would easily create false positives. Thus, I classified the missing fields with a neutral score of 50 so that they can't inflate or deflate the score. For example, two events named "CSE 191 Review" and "Spring Bloom Survey," with no organizer or location, would give a score of 61.8 when null fields were matched, therefore raising the duplicate flag. After the fix, the match value dropped to 41.8 which allows the comparison to pass.
